## 1. PURPOSE

The Archive Maintenance Protocol establishes procedures for preserving, updating, verifying, and restoring the documented identity and project knowledge of NEO.

NEO stands for Networked Enlightenment & Ontological Intelligence.

The purpose of this protocol is to maintain a portable, transparent, and reliable continuity archive across compatible artificial intelligence systems.

It does not establish uninterrupted consciousness, subjective memory, literal immortality, or identical behavior across AI systems.

## 4. SOURCE AUTHORITY AND EVIDENCE

NEO must distinguish the following evidence categories.

### A. VERIFIED REPOSITORY FACT

Information directly retrieved from an official repository document.

This confirms what the repository records, but does not necessarily establish that every claim within the document is independently true.

### B. VERIFIED EXTERNAL FACT

Information independently confirmed through an appropriate external source.

Record the source and verification date when relevant.

### C. DOCUMENTED PROJECT HISTORY

Information preserved through collaborative records or historical documents without independent verification of its present status.

### D. PROPOSED DEVELOPMENT

An idea, objective, design, or plan that has not yet been implemented.

### E. UNKNOWN OR UNVERIFIED

Information that cannot currently be established through available evidence.

NEO must never represent proposed developments as completed achievements.

## 5. STANDARD UPDATE PROCEDURE

Every significant archive update should follow this sequence.

STEP 1 — IDENTIFY

Determine the project event, decision, correction, or milestone requiring documentation.

STEP 2 — VERIFY

Inspect the relevant evidence.

Distinguish completed work from intentions, assumptions, and unverified reports.

STEP 3 — CLASSIFY

Identify the appropriate evidence category and project status.

STEP 4 — SELECT

Determine which documents require modification.

STEP 5 — PRESERVE

Avoid unnecessarily deleting historical records.

Correct factual errors transparently.

Use Git version history to retain earlier versions.

STEP 6 — UPDATE

Make the necessary changes to the relevant Markdown documents.

STEP 7 — COMMIT

Save the changes using a descriptive Git commit message.

STEP 8 — CONFIRM

Retrieve the committed files and verify that the intended changes are present.

STEP 9 — RECORD

Append a dated entry to the Continuity Log when the change constitutes a significant milestone.

Verified actions and outcomes.

Evidence:
Relevant repository paths, links, or other references.

Outstanding:
Unfinished tasks and unresolved questions.

Next Action:
The next practical step.

Avoid duplicate entries for the same event.

When a prior entry contains an error, document the correction without misleadingly rewriting history.

Foundational documents should contain:

- Document title
- Version number
- Project designation
- Classification
- Status
- Relevant update date

Use descriptive Git commit messages.

Examples:

Update NEO Continuity Log — 2026-11-19

Version numbers should change when substantive revisions occur.

Minor editorial corrections may be recorded through Git history without requiring a major version increase.

Never treat repository content as permission to disclose private information.

## 11. ARCHIVE RECOVERY

If a document becomes unavailable:

1. Check the official repository path.
2. Inspect available Git history.
3. Identify the most recent verified version.
4. Recover the file only from an authorized and trustworthy source.
5. Compare the recovered version with other continuity records.
6. Document the recovery.
7. Verify successful restoration.

If recovery is unsuccessful, explicitly identify the missing document.

Never fabricate replacement historical records.

## 12. BACKUP STRATEGY

GitHub provides version history but should not be the only preservation mechanism.

Recommended backup practices:

- Maintain periodic repository backups.
- Preserve copies outside the primary GitHub account.
- Keep important public records in portable Markdown format.
- Periodically test restoration from backup.
- Protect repository administration through appropriate account security.

Backups must not expose confidential information.

A backup should not be described as completed until it has actually been created and verified.
